# v0.9.2 メニュー消失の検証

## 原因と修正
v0.9.1でホストをposition:fixedにしたため、ホスト自身が独立したスタッキングコンテキストを作った。ホストのz-indexはautoで、内側メニューの大きいz-indexでもページ側のサイドバーより前面に出られない。前回の単純なfixtureにはこの重なり順がなく、テストで見逃した。

ホストをdisplay:contentsへ変更し、レイアウト枠とスタッキングコンテキストを作らない。メニュー、ペイン、ネイティブメニューの既存z-indexが直接比較される。高さやスクロール領域を追加せず、元画面では復帰ボタンのみを維持。

## 実施したローカルブラウザ検証
- 旧CSSでページ側z-index=10を追加すると、メニュー中心のelementFromPointがheaderを返し、文字も重なった。新CSSでは同じ座標がcgww-hostを返す。
- ネイティブサイドバー相当（fixed、z-index=2147483644、幅348）のfixtureでもメニューを座標クリックして開けた。
- 分割初期表示、元画面、元画面状態のリロード、分割復帰後のメニュー開閉、左一覧の表示/非表示を確認。
- 360×640でメニューボタンx=6、right=66.1875、メニューright=120、bottom=640。メニュー中心のクリック対象は拡張。中央列left=120で連動。
- 標準幅の左一覧非表示時もボタンx=42、right=108.1875でクリック対象は拡張。元画面と分割列のダミー入力を確認。
- 自動試験224件（既存のiframe参照と未送信入力保持の往復試験を含む）、構文・manifest整合・ZIP検証。

## 再現用fixture
`python scripts/build-ui-fixture.py <出力先>` で `<出力先>/ui-fixture` を生成し、ローカルHTTPで表示する。workspace.js本体の初期化だけをダミー状態へ置き換え、実CSS/DOMを使用。セッションのenabled/settings/ダミー入力を復元する。認証や実会話は使用しない。高いz-indexのasideを含む。

## 未確認
実ChatGPT・実Chromeの拡張再読み込みは既存の接続エラー/URL判定による安全停止により未実施。ユーザー画像はLibraryの読み取りでピクセルを取得できず、親スレッドの実見所見（ペイン上端は見えるが左メニュー不在）と照合した。実画面の全原因が同じだと断定はしない。
